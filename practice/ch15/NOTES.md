# K29《Building Agentic AI》第 15 章演練筆記：從提示詞工程師到系統架構師

> 快速 demo 模式，沒有經過 QA 或審查。書的 PDF 沒擷取到本章，內容依章名自行設計。

## 做了什麼

1. **唯讀瀏覽前五章成果**（沒有修改任何檔案）：
   - ch10 `patterns/`（ReAct、Reflection、Planning、Sequential）＋ `fake_llm.py`
   - ch11 `summarize_agent.py`（Agent SDK `query()`）
   - ch12 `tools.py`、`agent.py`（`claude -p` 決策者＋工具呼叫迴圈＋路徑沙盒）
   - ch13 `guardrails.py`、`agent.py`（白名單、覆寫確認、步數／成本預算、GuardLog）
   - ch14 `agent.py`、`grader.py`、`reflect_loop.py`、`evals/cases.json`（規則評分＋回饋重試）
2. **寫 `ARCHITECTURE.md`**，把它們組成「客服工單處理代理系統」：
   - ASCII 架構圖：入口 → 規劃 → 工具層（包在防護層裡）→ 評估迴圈 → 自動輸出／人工審核，附一張退款工單的完整路徑。
   - 元件來源對照表：每個元件標明章節、檔案、函式名稱與在系統中的角色。
   - 5 條 ADR：決策者選 `claude -p` 或 Agent SDK、防護放哪一層、人工審核的風險分級、規則評分或 LLM 評審、自我修正如何防作弊與防退步。
   - 缺口表（監控、記憶、部署、工具、安全、評估）與 7 步建議路線。

本章只產出設計文件，沒有新程式碼，也沒有執行測試。

## 從前面各章得到的關鍵設計輸入

- ch12：模型只「說」、程式才「做」，這讓防護層有地方插入。
- ch13：真模型實測觸發過成本煞車（每次 `claude -p` 約 $0.35 估算值），所以 ADR-001 把延遲與成本列為主要缺點。
- ch14：第 1 輪 0 分→第 2 輪 100 分，但回饋含期望值，有資料洩漏，這直接變成 ADR-005。

## 和書上做法的差異（依章名推測）

| 面向 | 本演練 | 書上可能的做法 |
| --- | --- | --- |
| 內容來源 | 用自己前五章的 demo 當元件，依章名組成系統 | 可能介紹通用的架構師思維、參考架構或案例研究 |
| 產出形式 | 一份設計文件（ASCII 圖＋ADR），沒有程式碼 | 可能附整合後的範例程式或框架（LangGraph 等）實作 |
| 決策者 | 選無狀態 `claude -p`，因為本機走 Max 訂閱、不設 API Key | 多半以 API Key＋Messages API／SDK 為前提 |
| 情境 | 自訂「客服工單處理」，延續 ch14 的客服分類題目 | 書上的範例情境不一定相同 |
| ADR 格式 | 情境／決策／取捨／替代方案 四段 | 標準 ADR 通常還有「狀態」「後果」欄位，這裡把後果併進取捨 |

## 已知限制

- 架構只是紙上設計，元件之間的介面（資料格式、例外傳遞）沒有實際接起來驗證過。
- 客服領域工具（查訂單、退款、寄信）都是假想，成本與延遲數字沿用 ch12～13 的實測，真實系統會不同。
- ADR-004 的混合評分權重（各 50%）和門檻 90 是假設值，需要用評估資料校準。
