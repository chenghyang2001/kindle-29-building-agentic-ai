# 客服工單處理代理系統：架構設計

> K29《Building Agentic AI》第 15 章「從提示詞工程師到系統架構師」演練。
> 本文件把第 10～14 章各自獨立的 demo 組成一個完整系統的**設計藍圖**（只有設計，沒有新程式碼）。
> 書 PDF 沒擷取到本章，內容依章名自行設計。

## 1. 系統目標

收到一張客服工單（Email／表單文字）→ 分類並抽出關鍵資訊 → 查詢訂單／物流等資料 → 產生回覆草稿或執行低風險動作（例如建立退款申請）→ 自動評分，不合格就自我修正，仍不合格或涉及高風險動作就轉人工審核。

設計原則（從「寫提示詞」轉向「設計系統」）：

1. **模型只做決策，程式才做動作**（第 12 章）：模型輸出 JSON 決策，執行權在程式手上。
2. **防護與決策分離**（第 13 章）：煞車寫在程式裡，不寫在提示詞裡，模型「說服」不了它。
3. **每個輸出都要能被量測**（第 14 章）：沒有評分就沒有自我修正，也沒有回歸測試。
4. **每一層都可以替換成假實作**（第 10、12～14 章的 `fake_*`）：整個系統不花錢就能跑完測試。

## 4. 架構決策紀錄（ADR）

### ADR-001：決策者用 `claude -p` 還是 Agent SDK

- **情境**：第 12～14 章用 `claude -p --output-format json` 每回合啟動一次 CLI；第 11 章用 `claude-agent-sdk` 的 `query()`。客服系統每張工單約 3～6 回合，要能完整記錄過程、並由程式掌控每個動作。
- **決策**：**主流程用 `claude -p` 當無狀態決策者**（模型只回 JSON，工具由我們的程式執行）。Agent SDK 留給「需要模型自己用內建工具探索」的子任務（例如讀一整個知識庫資料夾寫摘要）。
- **取捨**：
  - 優點：執行權完全在我們手上，防護層可以攔每一步；每回合無狀態，容易重放和測試；第 12、13 章已實測可用。
  - 缺點：每回合要重啟 CLI（約 20～40 秒、每次約 $0.35 估算成本，因為每次都帶完整系統提示）；要自己解析 JSON 和重試。
- **替代方案**：(a) 全面改 Agent SDK＋`can_use_tool` 回呼做防護——比較省事，但工具由 SDK 執行，防護要寫成回呼，較難單元測試。(b) 直接用 Messages API 的 `tool_use`——格式有保證、可平行呼叫，但要用 API Key 付費，違反本機「不設全域 API Key」的成本規則；上線規模變大時再評估。

### ADR-002：防護放在工具層還是代理層

- **情境**：第 12 章的路徑沙盒寫在工具函式裡（`_safe_path`）；第 13 章的白名單、覆寫確認、預算寫在代理迴圈裡（`guarded_execute`）。客服系統要加退款、寄信這類對外動作。
- **決策**：**兩層都要，分工明確**。
  - 工具層：只管「參數本身合不合法」（路徑沙盒、訂單編號格式、金額上限）。工具不管是誰呼叫都會檢查。
  - 代理層（防護層）：管「這一步該不該做」（白名單、風險分級確認、步數與成本預算、稽核紀錄）。
- **取捨**：
  - 優點：工具在別處重用時仍安全；代理層的政策可以依情境調整（例如夜間自動模式更嚴格），不用改工具。
  - 缺點：規則分散兩處，要在文件寫清楚哪條規則在哪層，避免重複或漏掉。
- **替代方案**：(a) 全放工具層——每個工具都要知道預算和審核，耦合太重。(b) 全放代理層——工具被其他程式直接呼叫時沒有保護。(c) 寫在提示詞裡請模型「不要做危險動作」——會被 prompt injection 繞過，只能當輔助。

### ADR-003：哪些動作需要人工審核

- **情境**：第 13 章只對「覆寫既有檔案」要求確認。客服情境的動作風險差很多：查訂單無害，退款會花錢，寄信給客戶無法撤回。
- **決策**：**依風險分三級**。
  - 低（讀取類：查訂單、查物流、讀政策）→ 直接執行。
  - 中（寫內部資料：草擬回覆、更新工單備註）→ 自動執行但記錄。
  - 高（對外或花錢：建立退款、寄信給客戶）→ 一律進人工待審佇列。
- **取捨**：
  - 優點：人只看真正有風險的事；系統初期可以安全上線。
  - 缺點：高風險動作的處理時間取決於人；退款量大時審核會塞車。
- **替代方案**：(a) 全部自動——風險不可接受。(b) 全部人工——等於沒有代理。(c) 依金額門檻自動核准小額退款——等評估資料累積、錯誤率可量測後再開放（見第 6 節）。

### ADR-004：評分用規則還是 LLM 評審

- **情境**：第 14 章用精確比對評分，可重現、成本零，但 `"高"` 和 `"high"` 會判錯；回覆草稿的語氣、是否符合政策無法用比對判斷。
- **決策**：**混合評分**。
  - 結構欄位（category、order_id、urgency、JSON 合法性）→ 規則評分（沿用 `grader.py`）。
  - 回覆草稿（語氣、是否承諾政策外的事、是否回答到問題）→ LLM 評審，用較便宜的 haiku，給評分標準與範例。
  - 總分 = 規則分 × 0.5 + LLM 評審分 × 0.5，門檻 90。
- **取捨**：
  - 優點：硬性欄位穩定、軟性品質也有量測。
  - 缺點：LLM 評審本身會不穩定、會偏好某些寫法，要定期用人工標註抽查評審。
- **替代方案**：(a) 全規則——量不到語氣。(b) 全 LLM 評審——成本高、不可重現，欄位錯誤可能被放過。(c) 只靠人工抽查——無法進自動修正迴圈。

### ADR-005：自我修正迴圈的範圍與防作弊

- **情境**：第 14 章的回饋帶了期望答案，第 2 輪拿 100 分有一部分是「抄答案」；也沒有防退步機制。
- **決策**：
  - **線上（處理單張工單）**：回饋只給扣分原因與規則，不給正解；最多 3 輪；保留歷輪最高分的草稿，不是最後一輪。
  - **離線（調提示詞）**：評估資料分成開發集與測試集；只用開發集產生回饋，用測試集驗收；新提示詞在測試集退步就不採用。
- **取捨**：
  - 優點：分數代表真實能力；不會越改越差。
  - 缺點：要維護兩份資料集；線上每多一輪就多一次模型成本與延遲。
- **替代方案**：(a) 不做自我修正，直接轉人工——成本低但人力負擔大。(b) 無上限修正直到滿分——成本與延遲失控，也可能過度迎合評分器。

## 5. 目前缺的部分

| 面向 | 現況（ch10～14） | 缺口 |
| --- | --- | --- |
| **監控／可觀測性** | 每次執行寫本地 `trace.json`、`guard-log.jsonl`、`scores.json` | 沒有集中儲存與儀表板；看不到每日成功率、平均成本、人工轉介率、防護觸發次數；沒有異常告警 |
| **記憶** | 每回合重組完整 prompt，歷史結果截斷 300 字（ch12、13）；工單之間完全無記憶 | 沒有同一客戶的歷史工單（短期對話記憶）；沒有「過去類似案例怎麼處理」的檢索（長期記憶／RAG）；沒有把人工修改過的回覆存回當範例 |
| **部署** | 本機命令列執行；`claude -p` 依賴本機登入 | 沒有佇列與 worker（工單進來自動處理）；沒有人工審核 UI；沒有重試／死信處理；沒有多租戶的權限與機密管理 |
| **工具** | 只有 CSV 讀取、統計、寫報告 | 客服領域工具（訂單、物流、政策、退款、寄信）都還是假想；需要真 API 或 mock 服務 |
| **安全** | 白名單、路徑沙盒、預算 | 沒有 prompt injection 偵測（客戶信件內容不可信任）、沒有輸出個資遮罩、成本是事後計量 |
| **評估** | 5 題規則評分 | 題目太少；沒有開發集／測試集分離；沒有 LLM 評審；沒有每次改提示詞自動跑的回歸測試 |

## 6. 下一步（建議順序）

1. **先接起骨架（離線）**：建一個 `ticket_agent/` 套件，把 ch12 的 `run_agent`、ch13 的 `guarded_execute`、ch14 的 `run_loop` 串成一條路；所有模型與工具都用假實作，先讓端對端測試通過。
2. **換上客服工具 mock**：`lookup_order`、`lookup_shipping`、`read_policy`、`draft_reply`、`create_refund_request`，加上 ADR-003 的風險分級。
3. **擴充評估集到 30～50 題**，切開發集／測試集，加 LLM 評審（ADR-004、005）。
4. **監控**：把三種 log 合成一筆「工單紀錄」（JSONL → SQLite），寫一個每日統計腳本（成功率、成本、轉人工率、防護觸發）。
5. **記憶**：同客戶的歷史工單摘要放進 prompt；人工核准的回覆存成範例庫，用關鍵字檢索帶入。
6. **部署**：工單佇列（資料夾輪詢或 SQLite 佇列）＋ worker 程式；人工審核先用簡單網頁（核准／退回）；最後才評估 n8n 或雲端排程。
7. **安全加強**：輸入端加 prompt injection 過濾（客戶信件一律當資料，不當指令）、輸出端加個資遮罩、改成呼叫前預估成本。
